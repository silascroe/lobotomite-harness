# Agent Lab audit — 2026-10-11

A full pass over the code, docs, tests, all 78 recorded runs under `agent-lab/runs/`, the console in a browser at desktop and phone widths, and the project's history. Written by Claude (Opus 5.5) on 2026-10-11. The "Fixed" section records what changed the same day; everything else is still open.

## Summary

The engineering is mostly sound: every suite passed before and after this audit, writes are atomic, resumes are careful, and the docs are honest about not being a sandbox. The weak point is the measurement. Most of the build effort went into Codex-style infrastructure (receipts, leases, approvals, review packets, repair episodes), while the parts that decide whether a run "passed" got much less attention. As a result the harness was measurably distorting its own results, and one serious security hole sat in the console.

## Security

The console had no authentication and accepted requests from any origin. A web page open in the same browser could POST to `127.0.0.1:8787` with a `text/plain` body (no CORS preflight), switch the provider to an endpoint it controls, and start a run against any folder. Because `run_command` allows `python script.py` for a script the model has just written, that endpoint could then make the harness write and run arbitrary code, and the next request would carry the configured API key to it. DNS rebinding reached the same API with readable responses. Recent Chrome may show a local-network permission prompt first; other browsers may not.

The console was also published several times through a Cloudflare tunnel without an authentication layer in front. No sign of abuse was found in the recorded runs or chats, which is reassuring but not proof.

Related: `allow_network` in `config.json` is not read by any code; the system prompt tells the model it cannot see outside the project, which `run_command` contradicts; and the claim that the model "cannot edit its own grading code" holds only for the file tools, not for scripts it runs.

What the numbers say: the plan gate is satisfied after the work is done and accepted that way, so it measures ritual compliance; "verify" is almost always a syntax check (even `python --version` would pass); the checkers are substring greps (a `<title>` tag alone satisfies "has a title field", and a working click handler fails `handles_submit`). Pass rates therefore measure protocol and form at least as much as whether the page works.

## Design

The console is competent visually and holds up at phone width. Information-design problems:

- The run page's most prominent text is the model's own finish summary, shown twice (header and success card). The evaluator verdict, first-pass vs repaired, call counts and failing checks should lead. The repaired pass inspected looked identical to a first-pass pass from the top of the page.
- Chats are listed only as timestamps (`chat-20260920-130301`); titles from the first message would fix most of the sidebar.
- The global Reasoning and Tools controls stay in the header while viewing a past run, showing the current setting rather than the run's (a run made at Off displayed "Standard").
- The header crowds: at 800px the workspace label overlaps the Reasoning label, and at phone width the select is clipped.

## Housekeeping

- Launch scripts point at Codex's private runtime (`.cache\codex-runtimes\...`) and fall back to `python`, which on this machine is the Microsoft Store stub.
- A stale local `master` branch sits beside `main`.
- `.git` is owned by the Codex sandbox account, so Git run as the normal user refuses the repo until `safe.directory` is set.
- `agent_harness.py` is about 2,600 lines. Splitting it is not worth doing for its own sake.
- Benchmark sampling uses temperature 0.6 with one sample per cell; any per-cell comparison is anecdotal until repeated.

## Fixed on 2026-10-11

| Change | Where | Evidence |
| --- | --- | --- |
| Console answers only loopback `Host`/`Origin` values and JSON POSTs; tunnels get 403 by design | `agent-lab/ui/server.py` | 4 new server tests; live replay of the cross-origin request returns 403/415 while the real console still loads and posts |
| A late `plan` checkpoint at implement/verify/review is always a recorded note, never a backward transition | `agent_harness.py` `workflow_checkpoint` | Regression test replaying the 002/003 Deep sequence |
| Local grammar is one schema per action with exact argument fields, enums and non-empty strings | `local_action_response_schema` | Schema/validator agreement test; live b11045 smoke test where Gemma, told to include `expected_replacements` and an invalid phase, could produce neither |
| Local prompt budget leaves room for the reply inside `model_context_tokens` (8192) with a 1.2x estimate margin | `request_context_budget`, `config.json` | Tests for local clamp and remote passthrough |
| A reply cut off at the token limit gets a specific "send smaller content" correction | run loop | Fake-model test |
| Atomic renames retry briefly on Windows sharing locks | `persistence.py` | Tests for transient and persistent locks |

## Follow-up the same day: measured reruns

The fixes above were measured with three full batches (36 runs) per harness version; details in the [2026-10-11 benchmark report](../agent-lab/benchmarks/2026-10-11-gemma-e2b-harness-fixes.md). With the fixes in the table above, 17 of 36 passed. Tracing those failures found three more general problems, all fixed:

- Evaluator findings arrive once and context compaction dropped them within about three turns, so repair episodes reread files without knowing what to fix. Open findings are now repeated on every repair request with a status line (edit, validate, review, or call finish now) derived from the project fingerprint and fresh evidence.
- A patch starting directly at `*** Update File:` without `*** Begin Patch` was fatal (four runs). It is now accepted, like the already-tolerated missing end marker.
- The duplicate-action refusal said only "choose a different action". It now names the next workflow step.

With those, 26 of 36 passed (p = 0.054 against 17 of 36), and repair episodes succeeded 9 of 15 times instead of 4 of 18 (p = 0.038).

One of these fixes was wrong the first time. The first version of the findings reminder repeated the findings without saying whether the model had already acted on them. In its one batch, 9 of 12 projects were correct but only 5 passed: the model repeated successful patches and validation because the reminder still said "edit these files", and the duplicate guard ended the runs. It was caught only because every project was graded afterward, not just the harness verdict, and that check should stay part of any future measurement. Suites after the follow-up: 143 harness, 6 checker, 44 UI-server, 4 benchmark, 27 UI contract.
